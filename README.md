# RAG for opencode (Phase 1: MCP only)

> Vector search over the infrastructure docs as an MCP tool the agent calls
> itself: opencode -> rag-core (MCP) -> Qdrant + CPU bge-m3 embedder.
> No LLM proxy, no Chatbox, no extra Prometheus/Grafana.

Retrieval stack for the infrastructure documentation corpus, kept as a
separate repository but attached to the main `llama.cpp` stack through the
shared external network `ai-net`.

The LLM (opencode) calls `search` itself when it needs to look something up:
opencode -> `rag-core` (MCP over HTTP) -> CPU embedder (bge-m3) + Qdrant ->
chunk text + source back to the agent. `rag-core` never calls the LLM in the
MCP path; the model decides.

```
opencode ──(MCP :8090 /mcp)──► rag-core ──► embedder :8081 (CPU, bge-m3)
                                  │   └────► qdrant :6333
                                  └──► corpus (read-only mounts)
```

## Services

| Service  | What it is | Notes |
| :------- | :--------- | :---- |
| `embedder` | the same pinned `llama.cpp` image as the main repo, `--embeddings -ngl 0` | CPU only; VRAM stays with the main model. No API key: unreachable from host and internet (`rag-net` is internal). |
| `qdrant`   | vector DB, own volume | keyed even on the internal network (`QDRANT__SERVICE__API_KEY_FILE`). |
| `rag-core` | one Python process: FastAPI + MCP SDK + qdrant-client | `/mcp` (opencode), `/ingest`, `/ingest/{id}`, `/health`, `/metrics`. Phase 1 publishes `127.0.0.1:8090` only. |

Networks: `rag-net` (bridge, `internal: true`) holds embedder + qdrant;
`ai-net` (external, created by `make init`) is shared with the main repo so
Phase 2 can reach `llama-server` by service alias. No LAN ports in Phase 1.

## Quick start

```
make init    # .env, secrets/{rag_api_key,qdrant_api_key}, docker network ai-net
make up      # builds rag-core, waits for embedder + qdrant to be healthy
make ingest  # full rescan of the corpus (patch mode: only changed files)
make search Q="how does the KV cache restore work"
```

Opencode MCP config (`~/.config/opencode/opencode.json`); the key is read
from the secrets file at startup, so it never sits in the config:

```json
{
  "mcp": {
    "rag": {
      "type": "remote",
      "url": "http://127.0.0.1:8090/mcp",
      "enabled": true,
      "headers": { "Authorization": "Bearer {file:/path/to/RAG/secrets/rag_api_key}" }
    }
  }
}
```

## Chunking and patching

* Markdown is split by headings (`##`/`###`); over-limit sections are split
  by paragraph, accumulated to `CHUNK_CHARS` (~2000), with a ~2-3 paragraph
  overlap. Code fences and tables are never split. Each chunk is stored with a
  breadcrumb `path > Section > Subsection` prepended.
* Point id = `UUID(sha256(path + chunk body)[:16])` (qdrant ids must be UUID
  or uint64); payload carries `path`, `section`,
  `start_line`, `end_line`, file `hash`, `mtime`, embedder `model`, `dim`.
* Incremental re-index ("patch"): `state.json` maps path -> mtime/hash. On
  `/ingest` a file is re-chunked only when mtime or hash changed; old points
  are deleted by `path`, then upserted. A full rescan is the safety net.
* The collection metadata records the embedder model and dim; writing with a
  different model/dim is refused (a model swap means a full reindex).

## Keys

Same pattern as the main repo: `secrets/` files, gitignored, generated by
`make init`. `rag_api_key` authenticates opencode to `rag-core` (all routes,
including `/mcp`). `qdrant_api_key` is mounted read-only into qdrant.

## Monitoring

`rag-core` exposes Prometheus text on `:8090/metrics` (embed/search/ingest
counters and durations, queue size). The main repo scrapes it: its prometheus
container joins `ai-net` and has a `job_name: rag` file_sd entry
(`prometheus/targets/rag.yml`) - no separate Prometheus or Grafana here.
A `rag` dashboard (status, search rate/latency, ingest counters) is
provisioned in the main repo's Grafana.

## Phase 2 (not built yet)

`/v1` OpenAI proxy + `+rag` virtual model for Chatbox: rag-core forwards
chat completions to `llama-server` over `ai-net` (alias `llama`), injecting
numbered sources as a system message for the RAG model. Port 8090 gets the
`LAN_IP` binding then.
